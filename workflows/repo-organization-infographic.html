Dynamics 365 CE · [A.3] Grounding · Type 3 — Coding assistants & agents

Three repositories, one agent session

A coding assistant grounds itself by reading. The design question is only ever “what must exist on disk, and where?”

Why three
Three questions recur throughout the delivery loop. They have different answers, different owners and different audiences — so they get different repositories.
01

What did the client ask for, and what does the environment currently look like?

<client>-Context/
02

What is actually built?

<client>-d365/
03

What does everyone else need to know about it?

<client>-wiki/
The shortcut that fails

Collapse them into one repository and it fails predictably: personal working notes end up in team pull requests, published documentation gets reviewed as if it were code, and the client’s shared repo accumulates material that was never cleared to live there.

Laying them out on disk
Clone all three as siblings under one parent folder, then make all three visible to the assistant at once.
<client>/
├── <client>-Context/   Intent + packs
├── <client>-d365/      Solutions + code
└── <client>-wiki/      Live documentation

VS Code / Cursor

A multi-root workspace (<client>.code-workspace) with the three folders as roots.

Claude Code

Add the other two as additional working directories, so it reads them without leaving the project repo.

Either way

Open the parent folder if the tooling supports it, so relative paths between the repos stay stable in prompts and scripts.

The payoff — one prompt that spans all three
Read the story in <client>-Context/1234-*, check it against the unpacked solution in <client>-d365/solutions/Core/src/, and tell me which wiki pages under Functional/ will need updating.

That question is unanswerable in any one repository alone.

Boundaries between them
Two placement decisions and two hygiene rules, all of them expensive to change later.

The zips stay out of git

The unpacked solutions/<Name>/src/ tree is the reviewable source of truth; the .zip is a rebuildable artifact.

Web resources flow one way

Either authored in webresources/ and deployed into the solution, or unpacked out of it. Mixing the two causes merge pain.

docs/ and the wiki are not duplicates

docs/ holds what belongs next to the code and is reviewed with it. The wiki holds what the wider engagement reads.

Each repo has its own trigger

Packs refresh on a re-export, the solution tree on every export/unpack, the wiki when behaviour changes.

Secrets

Connection strings, client secrets and .env files live in none of the three — the .gitignore excludes them explicitly.

Client data

The context repo does not become a dumping ground. Schema and metadata are a lower-stakes extract than live rows or PII, and the LEGAL.md notice travels with every pack.

Personal material

Story mirrors, drafts and notes stay in <client>-Context/. What graduates into <client>-d365/docs/ or the wiki does so deliberately, reviewed.
