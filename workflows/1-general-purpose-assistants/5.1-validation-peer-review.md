# [5.1] Validation / Peer Review / Close Out — design review, test scenarios, AC cross-checking, and the close-out checklist

> **Matrix cell:** [[5.1]](../ai-augmented-d365ce-activity-matrix.md#51-validation--peer-review--close-out) · Column **[1] General-Purpose AI Assistants** · Builds on [B.1](./b.1-initial-setup.md) + [C.1](./c.1-project-setup.md)

## What this activity is

- **Peer review** on pull requests, review of design docs (at the description/narrative level), check unit-test coverage, sanity-checking an approach, and cross-checking a delivered implementation *narrative* against the requirements doc.

- **Executing test plans** manually from acceptance criteria, may include integration testing, and automated testing -only if it uses distinct tooling from building-.

- **HITL discipline:** an AI review comes *after* the human has already reviewed, as a final detail-catcher — never as the first pass. First-pass AI feedback anchors the human reviewer and defeats the purpose of peer review.

- **Close-out** of the work-in-progress (WIP) solutions a story was built in, once the story is validated: their components reach the transport solutions that ship downstream, those transport solutions are checked, and the WIPs are deleted. A person carries it out; the assistant drafts the checklist and reviews what is pasted to it — see [Plan the close-out](#plan-the-close-out).

## Activities

### Sanity-check task completeness

```
Review this task list against the user story and its acceptance criteria.
What is missing? Check specifically for the tasks teams forget:
security role updates, solution/ALM steps, test data setup,
regression impact on existing forms/flows, and documentation.
[paste story + task list]
```

### Generate test cases from acceptance criteria

**AI:** Claude / Copilot Chat

```
Convert these Gherkin acceptance criteria into manual test cases
formatted for Azure DevOps Test Plans.
For each scenario, include: Test Case title, preconditions,
step-by-step actions, and expected result.
[paste acceptance criteria]
```

### Generate a UAT script

```
Write a UAT script for [feature] aimed at business users, not testers.
Plain language, one scenario per business task, using the real form and
view names from this Project's knowledge. Include the test data each
scenario needs and a pass/fail checkbox per step.
[paste feature description + ACs]
```

### Review a design document

```
Review this design document as a second reviewer — a human has already
reviewed it. Look for what detail reviews miss: internal contradictions,
requirements from the spec that the design silently drops, unstated
assumptions, and D365 CE anti-patterns (sync logic that should be async,
attribute bloat, security handled in JavaScript).
Report findings only; do not rewrite the document.
[paste or attach design doc]
```

### Cross-check an implementation narrative against requirements

```
Here is the requirements doc / user story, and here is the developer's
summary of what was implemented. List: (1) each AC and whether the
narrative claims to satisfy it, (2) ACs not addressed at all,
(3) implemented behavior that no AC asked for.
[paste both]
```

### Plan the close-out

A story is built in small, unmanaged **WIP solutions** — one per transport group, each holding only the components the story touches. What ships downstream are the **transport solutions** — the project's segmented solutions (Resources, Base, Security, Assemblies, Processes, Apps), deployed managed, in transport order. A WIP is never deployed downstream itself. Close-out ends each WIP once the story is validated.

A component the story *places* — a new column, an out-of-box form customized for the first time — has no transport home yet, so close-out has to put it somewhere that ships. A component edited *in place* already lives in a transport solution; its WIP only has to last until the edit has reached the transport source.

**The strategy follows the transport source.** Where each transport solution is extracted from decides how the WIPs feeding it end — per transport solution, not once per project. Where the project has CI/CD and ALM tooling, it is one of two:

| | A — Promote to build | B — Consolidate in development |
|---|---|---|
| **Applies when** | Transport solutions are extracted from a build environment, fed by a promotion pipeline | Transport solutions are extracted from development |
| **What close-out does** | A person runs the promotion for each WIP, which copies its components into the transport solution in the build environment; the transport solution is checked there; the WIP is deleted in development | A person adds the placement components to the transport solution in development, without required components; the transport solution is checked; the WIP is deleted. The next extract ships the work |
| **Isolation from in-flight work** | Yes — unfinished edits in development do not ship until promoted, apart from shared whole documents | No — any edit to a component already in transport ships with the next extract |

**Other strategies.** **C — Git-linked solutions**, where Dataverse Git integration binds solutions to a repository folder and a person commits from the maker portal,[^1] and **D — Power Platform pipelines**, where an in-product pipeline exports a solution when deployment is requested and deploys it stage by stage.[^2] These are not the only alternatives: solution patches merged back into their parent,[^3] a single unmanaged solution moved by hand, or a project's own pipelines each end work differently. The checklist below applies to all of them.

**Close-out checklist:**
```
Story [ID] is validated. Below are the components in its WIP solutions,
the project's segmentation map and transport order, and how each
transport solution is extracted. Draft the close-out checklist:
- the transport solution each component belongs to, and whether it is
  placed or edited in place;
- the close-out strategy for each destination, and why;
- the order to close out in — the whole story, in transport order;
- forms, views, sitemaps and ribbons another open story also changes;
- deletions a person must make separately in each environment;
- what to check in each transport solution afterwards.
Flag any component you cannot place. Do not assume a strategy the
material does not support — ask.
[paste component list + segmentation map + extraction notes]
```

**Dependency review:**
```
Here are the dependencies of the components in [WIP solution], from the
maker portal's dependency view or a failed import's message, and the
transport order. List every dependency on a component that sits in a
later transport solution, or in no solution at all — those would fail
the import downstream.
[paste dependency list + transport order]
```

## Review checkpoints

| Output | What the human checks |
|---|---|
| Test cases / UAT scripts | Steps executable against the real app; no invented form/field names |
| AI review findings | Triage each finding — the AI flags, the human decides severity and action |
| Sequencing of review | Confirm the human review happened **first**; AI findings appended, not leading |
| Close-out checklist | Each component's transport solution checked against the segmentation map; the strategy matches how that transport solution is really extracted; nothing added, moved or deleted on the assistant's word |
| Transport solution after close-out | Holds exactly what was intended, and the story's WIPs are deleted |

[^1]: Microsoft Learn — [Connect to Git](https://learn.microsoft.com/power-platform/alm/git-integration/connecting-to-git) (checked 2026-11-19). Environment or solution binding to a repository folder; commits from the maker portal.

[^2]: Microsoft Learn — [Overview of pipelines in Power Platform](https://learn.microsoft.com/power-platform/alm/pipelines) (checked 2026-11-19). The solution is exported when deployment is requested, and the same artifact passes through the stages in order.

[^3]: Microsoft Learn — [Implement a scalable ALM approach by using Microsoft Package Deployer](https://learn.microsoft.com/power-platform/architecture/reference-architectures/implement-alm-approach) (checked 2026-11-19). A reference architecture that merges patch components into the parent solution, deletes the patch, and ships the fix with the next extract.
