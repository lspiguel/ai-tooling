# [1.3] Specification / Intent — grounded gap analysis and technical specs that name real components

> **Matrix cell:** [[1.3]](../ai-augmented-d365ce-activity-matrix.md#13-specification--intent) · Column **[3] Coding Assistants & Agentic Environments** · Builds on [B.3](./b.3-initial-setup.md) + [C.3](./c.3-project-setup.md)

## What this activity is

- **Capturing intent** by describing what is expected to be constructed and what it should provide to the overall system, and where necessary describing how that fits into the architecture and design.

- **Turn raw stakeholder input** (meeting notes, emails, workshop whiteboards) into the **epic → feature → user story hierarchy** with acceptance criteria that follow the house templates seeded in the [B.3] Project.

- **Deliverables** are the user story/stories with complete:
1. Title
2. Intent/Description
3. Acceptance Criteria
4. Attachments or reference materials
This would need to be pushed into the Work Management Platform (ADO, Jira, etc) for collaboration and management.

Write user stories & ACs — concentrating on providing **intent and acceptance criteria** rather than prescribing the implementation. Use **Ask Mode** to explore options for ACs before committing to one formulation, review and/or formulate possible exception scenarios. The reconciliation against what exists is **deeper**, because the assistant is sitting in the grounded repo:

- The **unpacked solution tree** (`solutions/<Name>/src/`) lets the gap analysis cite real files: the actual plugin steps, form XML, and web resources a change will touch.
- **Azure DevOps CLI** (`az boards`) pulls the related existing work items, so the spec doesn't duplicate what's already in the backlog.
- **Dataverse MCP**, where it is registered, confirms a specific table or column against the live environment when the repo state looks stale. It is a spot-check, not the grounding — see [[A.iii]](../ai-augmented-d365ce-activity-matrix.md#aiii-dataverse-mcp-server--column-3).

## Activities

### Grounded gap analysis for a new requirement

**AI:** Copilot agent mode / Claude Code
**Context:** Repo root, Azure DevOps CLI available

```
New requirement: [describe requirement].
Produce a gap analysis:
1. Read the unpacked solution and the context packs to check which tables
   and columns already cover part of this — cite logical names and the
   files you read them from.
2. Search the solutions for existing plugins, flows, forms,
   and web resources that implement related behavior — cite file paths.
3. Query ADO for open or closed work items touching the same area.
4. Conclude: what exists, what must change, what is net-new.
Do not propose an implementation yet.
```

### Explore options in Ask Mode

```
In ask mode (no edits): here is the intent and the draft acceptance criteria
for [requirement]. Lay out the implementation options this environment
supports, each option's trade-offs given the unpacked solution and live
schema, and the questions we'd need answered before choosing.
Do not write the spec or any code yet.
```

### Check the backlog for duplication

**Context:** Azure DevOps CLI (`az boards work-item query`)

```
Search our Azure DevOps project for existing work items related to
[feature/table/process]. List ID, title, state, and how each relates to
this new requirement — duplicate, prerequisite, or superseded.
```
