# [5.3] Validation / Peer Review / Close Out — conventions-aware code review, drift detection, PR hygiene, WIP close-out

> **Matrix cell:** [[5.3]](../ai-augmented-d365ce-activity-matrix.md#53-validation--peer-review--close-out) · Column **[3] Coding Assistants & Agentic Environments** · Builds on [B.3](./b.3-initial-setup.md) + [C.3](./c.3-project-setup.md)

## What this activity is

- **Peer review** on pull requests, review of design docs (at the description/narrative level), check unit-test coverage, sanity-checking an approach, and cross-checking a delivered implementation *narrative* against the requirements doc.

- **Executing test plans** manually from acceptance criteria, may include integration testing, and automated testing -only if it uses distinct tooling from building-.

- **HITL discipline:** an AI review comes *after* the human has already reviewed, as a final detail-catcher — never as the first pass. First-pass AI feedback anchors the human reviewer and defeats the purpose of peer review.

- **Ask Mode with an adversary reviewer prompt** for automated review: a consistent, explicit rule set (StyleCop, prefixes, no early binding, fixture coverage) gives consistent, conventions-aware review — better than ad-hoc prompting the same rules each time.

- **Close-out** of the work-in-progress (WIP) solutions a story was built in, once the story is validated: their components reach the transport solutions that ship downstream, those transport solutions are read back, and the WIPs are deleted. How that happens depends on where each transport solution is extracted from — see [Close out](#close-out--wip-solutions-into-transport-solutions).

## Activities

### Code review (after the human pass)

**AI:** GitHub Copilot Chat / reviewer persona
**Context:** the PR diff / plugin class

**Best-practices review:**
```
Review this plugin class for the following: unnecessary catch blocks that
rethrow without adding information, missing null checks,
any hardcoded GUIDs or magic strings that should be constants,
and any N+1 query patterns.
```

**Style conformance:**
```
Correct this code to conform to StyleCop style,
add missing documentation comments.
```

**JS quality:**
```
What JS styling and quality rules from SonarQube or ESLint
could be applied to this code? List each issue with the line reference.
```

**Dead code sweep:**
```
Is there any dead code, commented-out code, or duplicate functions
across these files? List findings with file and line number.
```

### Unit-test coverage check

```
Compare the unit tests on this branch against the unit test conditions
defined in task [ID]'s description. List: conditions with no covering test,
tests that assert nothing from the conditions, and branches in the changed
code with no test at all.
```

### Test cases and UAT scripts from the ACs

**Context:** the story folder in `<client>-Context/` + the unpacked solution

**Test cases for Azure DevOps Test Plans:**
```
Convert the Gherkin acceptance criteria in story [ID] into manual test cases
formatted for Azure DevOps Test Plans. For each scenario: Test Case title,
preconditions, step-by-step actions, and expected result. Use the real form,
view, and field names from the unpacked solution — cite the component files
you took them from, and flag any AC that can't be tested against what the
repo actually contains.
```

**UAT script for business users:**
```
Write a UAT script for story [ID] aimed at business users, not testers.
Plain language, one scenario per business task, using the real form and view
names from the unpacked solution. Include the test data each scenario needs
and a pass/fail checkbox per step. Save it to the story folder in
<client>-Context/ for review.
```

### Configuration review

**Naming conventions across the solution:**
```
Review the customizations in this solution folder.
Flag any table, field, form, view, or flow names that do not follow
the prefix convention "[prefix]_" or that use default system-generated names.
```

**Flows — error handling and performance:**
```
Identify cloud flows in this folder that do not have a "Configure run after"
or scope-based error handling. List them with their trigger.
```
```
Which flows in this folder iterate over collections using Apply to Each?
List them and note if parallel branching is enabled.
```

### Security review

**Context:** security solution folder

```
Analyze the security role definitions in this folder.
Flag any roles that have organization-level access on sensitive tables
such as SystemUser, Team, or BusinessUnit.
```

### Power Pages review

**Security:**
```
Review these Liquid template files and flag any places where user input
is rendered without escaping, or where table permissions are bypassed.
```

**Accessibility and UX:**
```
Review this Power Pages web template Liquid code for accessibility issues:
missing alt text, poor heading hierarchy, form labels not associated with inputs,
and interactive elements not keyboard accessible.
```

### Solution health / technical debt

**Repository sweep:**
```
Review this solution repository. Flag: deprecated APIs,
hardcoded environment URLs, plugins running synchronously that could be async,
flows using legacy connectors, and any components using unsupported patterns
for the current Power Platform version.
```

**Identify unused components:**
```
Are there any tables, fields, flows, or web resources on items modified by
this story that appear to have no references in forms, views, plugins,
or other flows?
```

### PR description + self-review

```
Generate the PR description for this branch: summary of the change,
components touched (real paths), how it satisfies the story's ACs
(reference [story ID]), test evidence, and anything the reviewer should
look at first. Then do a self-review pass and list the concerns you'd
raise if this were someone else's PR.
```

### Close out — WIP solutions into transport solutions

**Context:** the story's WIP solutions in development, the segmentation map and transport order, the pipeline definitions in `<client>-d365/`

A story is built in small, unmanaged **WIP solutions** — one per transport group, each holding only the components the story touches. What ships downstream are the **transport solutions** — the project's segmented solutions (Resources, Base, Security, Assemblies, Processes, Apps), extracted into `<client>-d365/` and deployed managed, in transport order. A WIP is never deployed downstream itself. Close-out ends each WIP once the story is validated.

**Two routes per component.** A component the story *places* has no transport home yet — a new column, an out-of-box form customized for the first time — so its WIP needs close-out to put it somewhere that ships. A component edited *in place* already lives in a transport solution; its WIP only has to last until the edit has reached the transport source.

**The strategy follows the transport source.** Where a destination transport solution is extracted from decides how the WIPs feeding it end. It is settled per transport solution, not once per project, and never assumed: derive it from the pipeline definitions and the environments, and ask when they do not settle it.

Where the project has CI/CD and ALM tooling — an extract-and-commit pipeline, and possibly a build environment with a promotion pipeline — close-out is one of two strategies:

| | A — Promote to build | B — Consolidate in development |
|---|---|---|
| **Applies when** | Transport solutions are extracted from a build environment, fed by a promotion pipeline | Transport solutions are extracted from development |
| **What close-out does** | A person runs the promotion for each WIP: the pipeline imports it into the build environment and copies its components into the transport solution there. The transport solution is read back on the build environment, then the WIP is deleted in development | Placement components are added to the transport solution in development — without required components or subcomponents — the transport solution is read back, and the WIP is deleted. The next extract ships the work |
| **In-place WIPs** | Promoted too: the edit reaches transport only through promotion | End at import and validation; the edit ships with the next extract |
| **Isolation from in-flight work** | Yes — development's unfinished edits do not ship until promoted, apart from shared whole documents | No — any edit to a component already in transport ships with the next extract, whatever its WIP's state |
| **What validates placement** | The promotion pipeline, as a backstop; the plan is to shape the WIP right so promotion passes first time | Only the person approving each add |

**Other strategies.** Two more are named here so they are recognised, not covered:

- **C — Git-linked solutions.** Dataverse Git integration binds the environment or individual solutions to a repository folder, and a person commits from the maker portal in the YAML source layout.[^1]
- **D — Power Platform pipelines.** In-product pipelines export a solution from its source environment when a deployment is requested and deploy that same artifact, managed, stage by stage.[^2]

These are not the only alternatives. Solution patches merged back into their parent,[^3] a single unmanaged solution moved by hand, or a project's own pipelines each end work-in-progress differently. Whatever the mechanism, the checks below still apply; work out how each is met under it before an agent prepares a close-out for it.

**What every close-out checks:**

| Check | Why |
|---|---|
| **Dependencies point down the transport order** | WIPs leave out required components, so everything a component needs must already be where it lands — in an earlier transport solution, or in this story's WIP for an earlier group that closes out first |
| **The whole story, in transport order** | Closing out one WIP at a time lets a build in between carry half a story; no automated deployment runs between them |
| **Shared whole documents** | Forms, views, sitemaps, ribbons and web resources travel whole: another story's unfinished edit to the same form goes along |
| **Deletions are separate** | Removing a column, view or step is a person's task in each environment transport is extracted from, followed by the managed upgrade that removes it downstream |
| **The transport solution is read back** | Only the intended components are new; anything else goes straight into the next extract |
| **No leftover WIPs** | Stale WIPs distort the overlap checks of the next story |

#### Agentic close-out with the Agent Companion MCP

With the [Agent Companion MCP](/tooling/D365AgentCompanionMcp/README.md) connected, the [`agent-companion-wip-close-out`](/skills/agent-companion-wip-close-out/SKILL.md) skill carries out strategies A and B. It checks dependencies against the transport order, adds placement components to the transport solution under B, prepares each promotion run under A and verifies it through a second plugin tab bound read-only to the build environment, then deletes the WIPs and looks for leftovers. [`agent-companion-context`](/skills/agent-companion-context/SKILL.md) derives each WIP's strategy and keeps the WIP ledger. For C or D, the skills stop and ask how to proceed.

The agent states the steps and a person confirms them before anything changes. A person approves every call in the plugin, and runs every pipeline, commit and push.

**AI:** coding agent with the Agent Companion MCP
**Context:** the WIP ledger for story [ID]; the development connection, and under A the build connection

**Close out a story:**
```
Story [ID] is validated. Close out its WIP solutions. Before any Write
call, state the steps: each WIP with its route and destination, the
strategy for each destination and the evidence for it, the dependency
check, the order, the pipeline runs I have to start, and when each WIP
is deleted. Wait for my confirmation.
```

**Verify a promotion:**
```
I ran the promotion for [WIP name]. On the build connection, check that
its components are in [transport solution] with the same behaviours,
that nothing else is new there, and that the WIP is gone from build.
Then tell me whether the WIP in development can be deleted.
```

**Leftover WIPs:**
```
List the WIP solutions in development that the ledger does not know,
or whose work item is closed. Report them; delete none.
```

#### Without the plugin

The coding agent can still prepare a close-out from the repository — establish each transport solution's source from the pipeline definitions, place each component against the segmentation map, and find dependencies that point up the order. A person carries it out in the environment.

```
From the pipeline definitions in <client>-d365/, tell me where each
transport solution is extracted from and which close-out strategy that
implies. Then, for the WIP unpacked at [work folder], list each component,
its transport group per the segmentation map, and every missing dependency
in its Solution.xml that sits in a later group or in no solution at all.
```

## Review checkpoints

| Output | What the human checks |
|---|---|
| Persona/AI findings | Triage each; human decides severity — the AI never blocks or approves a PR |
| Test cases / UAT scripts | Steps executable against the real app; cited form/field names verified, none invented |
| Security findings | Verify against the actual org before acting |
| Close-out steps | The strategy for each destination matches where it is really extracted from; the whole story, in transport order; deletions listed as person tasks |
| Pipeline runs, commits and pushes | A person runs each one; no WIP is deployed downstream |
| Transport solution after close-out | Shows exactly what was intended — on development under B, on the build environment under A |
